# LangChain · ChatPromptTemplate · LCEL
## Python으로 설계하는 안내문 생성 체인 — 8교시 이론 교안

오늘의 결과물은 **독자·어조·공지 사실을 입력받아 안내문을 생성하는 Python 체인**이다. 처음에는 메시지 한 번을 만들어 보고, 마지막에는 입력을 검증하고 원문과 요청 ID를 보존하는 작은 서비스 로직을 직접 설계한다. 합성 사내 공지를 사용하며 실제 이메일 전송은 하지 않는다.

이 교안은 2번째 단위 ‘단일 에이전트 추론 및 AI 오케스트레이션’의 첫 항목에 해당한다. 앞서 경험한 Python 함수·딕셔너리·가상환경·예외 처리를 다시 사용한다. FastAPI의 요청 검증을 배웠다면 오늘의 입력 검증과 연결할 수 있다. 다만 개인별 숙달은 1교시 진단으로 확인한다. 다음 항목에서는 오늘 만든 프롬프트와 체인 인터페이스에 문제 분해·추론 전략을 적용한다.

**시간 가정:** 1교시 50분, 총 400분의 수업 활동이다. 쉬는 시간은 별도이며 공식 시간표가 제공되면 조정한다. 각 교시는 다음과 같이 완결된다.

| 교시 | 핵심 질문 | 새로 익힐 개념 | 종료 산출물 |
| --- | --- | --- | --- |
| 1 | 모델 호출 전에 무엇을 준비하는가? | 가상환경, 패키지, 메시지, invoke | 설치 확인·첫 응답·타입 기록 |
| 2 | 바뀌는 값과 고정 규칙을 어떻게 나누는가? | 역할, 템플릿 변수, partial | 독자·어조·사실 템플릿 |
| 3 | 세 객체를 왜 파이프로 연결하는가? | Runnable, LCEL, 파서, 타입 계약 | 문자열을 반환하는 체인 |
| 4 | 프롬프트 개선을 어떻게 비교하는가? | 통제 변수, 기준선, 사람 평가 | A/B 비교 기록 6건 |
| 5 | 실패한 위치를 어떻게 찾는가? | 변수 누락, 타입·길이, 중괄호 | 원인·수정·회귀 검증 |
| 6 | 다음 단계에 원문을 어떻게 남기는가? | RunnableLambda, assign, 순차 통합 | 원문·초안·검토 dict |
| 7 | 새 입력 여러 개를 스스로 처리할 수 있는가? | batch, 동시성, stream 선택 | 직접 작성한 배치 체인 |
| 8 | 요구사항에서 체인을 설계할 수 있는가? | 입력·출력 계약, 메타데이터 보존 | 요청 ID가 보존된 종합 서비스 |

이론은 이 README 순서대로 읽고, 실제 작성·실험·평가는 [WORKBOOK.md](WORKBOOK.md)에서 진행한다. 1~6교시는 작은 완성 예제를 관찰하고 확장한다. 7~8교시는 시작 코드에 로직을 직접 작성한다. `solutions/`는 시도한 뒤 확인할 해설이다.

## 실행환경과 실행방법

### Python과 가상환경

검증 기준은 **Python 3.12, 격리된 venv**이다. 압축을 풀고 `README.md`와 `requirements.txt`가 보이는 `LangChain_8Sessions` 폴더를 VSCode에서 연다. 터미널의 현재 위치도 이 폴더여야 한다. 아래의 `python`은 활성화한 가상환경의 Python을 뜻한다.

Windows CMD:

```bat
py -3.12 -m venv .venv
.venv\Scripts\activate.bat
python -m pip install -r requirements-lock.txt
```

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-lock.txt
```

PowerShell에서 활성화 스크립트가 차단되면 정책을 바꾸지 않고 가상환경 실행 파일을 직접 사용한다.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m lessons.s01_environment.main --mock
```

Linux/macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-lock.txt
```

설치가 끝나면 다음을 확인한다.

```bash
python --version
python -m pip check
python -c "import sys; print(sys.executable)"
```

`requirements.txt`는 주요 패키지 버전을, `requirements-lock.txt`는 이번 Python 3.12 환경의 전체 설치 버전을 기록한다. 수업 도중 무제한 업그레이드를 실행하지 않는다. Windows/macOS에서는 동일 잠금 파일로 설치하되, 플랫폼별 설치 성공 여부는 각 PC에서 확인해야 한다. 설치 오류가 나면 Python 버전과 가상환경 경로부터 확인한다.

### API 설정

`.env.example`을 복사해 같은 폴더에 `.env`를 만든다. CMD에서는 `copy .env.example .env`, PowerShell에서는 `Copy-Item .env.example .env`, Linux/macOS에서는 `cp .env.example .env`를 사용한다. 제공받은 OpenAI 키를 본인 PC의 `.env`에만 넣는다.

```dotenv
LLM_PROVIDER=openai
OPENAI_API_KEY=replace-with-provided-key
OPENAI_MODEL=gpt-4.1-mini-2025-04-14
GROQ_API_KEY=
GROQ_MODEL=openai/gpt-oss-20b
LANGSMITH_TRACING=false
```

실제 키는 제출·화면공유·Git 커밋 대상에서 제외한다. 기존 환경변수가 있으면 그 값이 `.env`보다 우선한다. 수정한 `.env`가 반영되지 않으면 현재 터미널에 같은 이름의 환경변수가 있는지 확인한다. 키 값을 화면에 출력하지 않는다.

기본 실습 모델은 계정에서 접근 가능한 **GPT-4.1 mini의 날짜 고정 ID**로 설정했다. 2026-11-13 확인 기준 이 계열은 2027-01-14 종료 예정 안내가 있으므로, 그 이후 수업에서는 제공 계정에서 사용 가능한 모델로 `OPENAI_MODEL`을 변경하고 파라미터 호환성을 다시 확인한다. 이 예제는 `temperature=0`, 출력 상한 350토큰을 지원하는 채팅 모델을 전제로 한다. 모델 ID만 바꾸었다고 모든 파라미터가 호환되는 것은 아니다.

수업 전 [공식 모델 안내](https://developers.openai.com/api/docs/models/gpt-4.1-mini)와 [종료 일정](https://developers.openai.com/api/docs/deprecations)에서 사용 가능 여부를 다시 확인한다.

API가 없는 상태에서는 명시적으로 `--mock`을 붙인다. 이 모드는 항상 같은 합성 응답을 돌려준다. **템플릿·파이프·출력 타입을 연습할 수 있지만 실제 모델의 문장 품질·사실 준수·속도를 평가할 수 없다.**

```bash
python -m lessons.s01_environment.main --mock
python -m lessons.s01_environment.main
```

첫 명령은 원격 호출이 없다. 두 번째 명령은 OpenAI를 실제 호출한다. 실행은 완료되면 종료되며, 대기 중 중단은 `Ctrl+C`, 가상환경 종료는 `deactivate`이다. `.env`는 압축에 포함되어 있지 않다.

### 차시별 실행

모든 명령은 압축을 푼 최상위 폴더에서 실행한다. 하위 폴더의 `main.py`를 직접 실행하면 `common` 모듈을 찾지 못할 수 있으므로 `-m` 방식으로 실행한다.

| 교시 | 로컬 연습 명령 | 실제 호출 수/명령 1회 |
| --- | --- | ---: |
| 1 | `python -m lessons.s01_environment.main --mock` | `--mock` 제외 시 1 |
| 2 | `python -m lessons.s02_prompt.main` | 0 |
| 3 | `python -m lessons.s03_lcel.main --mock` | `--mock` 제외 시 2 |
| 4 | `python -m lessons.s04_compare.main --mock` | `--mock` 제외 시 6 |
| 5 | `python -m lessons.s05_diagnose.main` | 0 |
| 6 | `python -m lessons.s06_integrate.main --mock` | `--mock` 제외 시 2 |
| 7 | `python -m lessons.s07_independent.main --mock` | 구현 후 실제 실행 시 2, stream 추가 시 +1 |
| 8 | `python -m lessons.s08_capstone.main --mock` | 구현 후 실제 실행 시 1 |

7·8교시 시작 코드는 구현 전 의도적으로 실행을 완료하지 않는다. 해당 교시 요구사항에 따라 작성한 뒤 실행한다. 해설 실행 명령은 각각 `python -m solutions.session07 --mock`, `python -m solutions.session08 --mock`이다. 처음부터 해설을 복사한 작업은 독립 수행의 증거로 제출하지 않는다.

Groq 선택 실행은 7교시에만 추가해도 된다.

```bash
python -m solutions.session07 --provider groq
```

`.env`의 `GROQ_API_KEY`와 계정에서 지원하는 `GROQ_MODEL`이 필요하다. 무료 플랜의 계정별 모델 접근 가능 여부와 조직 단위 요청·토큰 제한을 확인한다. 무료는 무제한을 뜻하지 않는다. 실패해도 OpenAI로 자동 전환하지 않는다. 모의 모드에서 `stream`을 실행하면 보통 전체 문자열 한 덩어리가 나오며 토큰 단위 실시간 생성의 증거가 아니다.

### 비용과 호출 예산

기본 완성 경로를 교시별 한 번씩 실제 실행하면 **14회** 호출한다. 1교시 1회 + 3교시 2회 + 4교시 6회 + 6교시 2회 + 7교시 2회 + 8교시 1회다. 선택 스트리밍은 1회 추가, 반복 실험과 오류 후 재실행은 별도다. 자동 재시도는 꺼 두었다.

2026-11-13 확인한 GPT-4.1 mini 일반 텍스트 가격은 입력 100만 토큰당 $0.40, 출력 100만 토큰당 $1.60이다. 예를 들어 **호출당 입력 800토큰·출력 350토큰이라고 가정**하면 14회는 약 $0.01232다. 실제 토큰 사용·캐시·계약·세금·가격 변경은 별도이며 비용 보장값이 아니다. 글자 수는 토큰 수와 다르다. 4교시 로그의 usage와 제공 계정 대시보드를 확인하고, 전체 수강생 호출량은 계정 공유 여부에 맞춰 합산한다.

### 실행 오류의 복구 순서

| 증상 | 먼저 확인할 것 | 복구 후 확인 |
| --- | --- | --- |
| `ModuleNotFoundError` | 현재 폴더, `sys.executable`, 설치 환경 | 같은 Python으로 pip 실행 후 재실행 |
| 설정 안내문 | `.env` 파일명, 모델 ID, 해당 키의 존재 | 키를 출력하지 않고 1회 실행 |
| 템플릿 `KeyError` | `input_variables`와 입력 dict의 키 | 모델 없이 `prompt.invoke`만 실행 |
| 400 | 파라미터·입력 형식·모델 지원 | 공식 지원 범위에 맞춘 뒤 1회 실행 |
| 401/403 | 키 만료·프로젝트·모델 권한 | 권한을 확인하고 수동 재실행 |
| 404 | 모델 ID와 계정에서의 가용성 | 접근 가능한 ID로 수정 후 재검증 |
| 429 | 요청/토큰 한도 또는 결제 할당량 | 서버 대기 안내와 계정 상태 확인 후 수동 재실행 |
| 타임아웃 | 네트워크·서비스 상태 | 모의 실습으로 전환해 진행하고 원격 재검증 |

이 수업 코드는 재시도 루프를 자동으로 돌리지 않는다. 운영 서비스에서 재시도가 필요하면 429/일시적 오류만 대상으로 `Retry-After`를 존중하고 지수 백오프·지터·최대 시도 수·최대 대기를 함께 설계한다. 400/401/403을 그대로 반복 요청해 해결하려 하지 않는다.

## 1교시. LangChain은 무엇을 연결하는가?

### 1.1 직접 호출과 프레임워크의 역할

Python에서 모델 API를 호출하는 것 자체는 공급자의 SDK만으로도 가능하다. 그러나 실제 업무에는 입력 정리, 프롬프트 작성, 모델 호출, 응답 변환, 다음 함수로 전달하는 과정이 함께 필요하다. LangChain은 이 구성 요소들을 일정한 호출 규칙으로 연결하는 도구를 제공한다.

예를 들어 ‘교육 공지를 작성해 달라’는 작업에는 다음 정보가 필요하다.

| 정보 | 예 | 프로그램에서의 위치 |
| --- | --- | --- |
| 고정 업무 규칙 | 없는 날짜를 만들지 말 것 | system 메시지 |
| 이번 요청의 값 | 독자, 어조, 공지 사실 | 입력 dict |
| 호출 대상 | 제공 계정에서 사용 가능한 모델 | 모델 객체 |
| 결과의 사용 형태 | 콘솔·파일에 넣을 문자열 | 출력 파서 이후 |

프레임워크를 사용한다고 모델이 자동으로 회사 정보를 아는 것은 아니다. 오늘의 사실 정보는 우리가 입력으로 준 공지뿐이다. 데이터베이스 검색, 외부 도구, 대화 기억, 자율적인 계획은 아직 구현하지 않는다. **미리 정한 순서로 실행되는 체인과 상황에 따라 행동을 선택하는 에이전트는 구별한다.**

### 1.2 패키지는 왜 나뉘어 있는가?

`langchain-core`는 메시지·프롬프트·Runnable·파서 같은 공통 기반을 제공한다. `langchain-openai`는 OpenAI 모델을 연결하는 통합 패키지다. `langchain-groq`는 Groq 연결에 사용한다. `langchain`은 더 넓은 프레임워크 패키지이며, 오늘 코드의 핵심 import는 `langchain_core`와 공급자 패키지에서 가져온다.

설치 이름의 하이픈과 Python import의 밑줄도 구별해야 한다.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
```

Python 가상환경은 프로젝트별 패키지를 분리한다. A 프로젝트를 위해 올린 버전 때문에 B 프로젝트의 수업 코드가 깨지는 일을 줄일 수 있다. `python -m pip`를 사용하는 이유는 현재 선택된 Python에 설치하려는 의도를 분명히 하기 위해서다.

### 1.3 메시지와 invoke

채팅 모델 입력은 역할을 가진 메시지들의 모음으로 표현한다. 오늘 사용하는 `system`은 업무 규칙, `human`은 이번 요청을 담는다. 생성된 응답은 일반적으로 `AIMessage`로 관찰한다.

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "한국어로 한 문장만 답하세요."),
    ("human", "{question}"),
])
value = prompt.invoke({"question": "템플릿은 왜 사용하나요?"})
response = model.invoke(value)
```

첫 번째 `invoke`는 템플릿에 값을 채워 메시지를 만드는 작업이다. 여기에는 모델 API 호출이 없다. 두 번째 `invoke`는 모델 객체를 실행하는 작업이므로 실제 모드에서는 원격 호출이 발생한다. 같은 메서드 이름을 쓰더라도 **어떤 객체에 호출하는지**에 따라 일이 달라진다.

`prompt.invoke` 결과는 `ChatPromptValue`이며, `.to_messages()`로 실제 메시지 목록을 확인할 수 있다. 모델 결과의 `.content`는 오늘의 텍스트 예제에서는 문자열이지만, 도구·이미지 등을 포함한 모든 모델의 content가 항상 단순 문자열이라고 일반화하지 않는다.

### 1.4 첫 실행에서 관찰할 것

1교시 코드는 패키지 버전, 렌더링 결과 타입, 응답 타입을 출력한다. `[MOCK: 품질평가 제외]`가 있으면 합성 응답이다. 실제 응답은 문장이 예시와 같을 필요가 없다. 이번에는 **환경이 맞는지, 모델 앞 단계와 모델 단계를 구분하는지**가 성공 기준이다.

선수 진단에서는 `dict`의 없는 키를 읽을 때의 결과, 함수의 반환값, 가상환경의 역할을 확인한다. 답이 어려우면 모델 설명에 앞서 `data={"name":"민수"}`에서 `data["name"]`과 `data["age"]`를 실행해 차이를 관찰한다.

## 2교시. ChatPromptTemplate은 입력 계약이다

### 2.1 고정 문장과 가변 값

매번 문자열을 붙여 프롬프트를 만들면 어떤 값이 누락되었는지 찾기 어렵다. 템플릿은 고정 문장과 변경할 값을 분리한다. `{audience}`처럼 중괄호로 지정한 자리는 **Python 변수가 아니라 템플릿이 요구하는 변수 이름**이다.

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "제공된 사실만 사용해 안내문을 작성하세요."),
    ("human", "독자: {audience}\n어조: {tone}\n사실: {notice}"),
])
```

이 템플릿의 필수 입력은 `audience`, `tone`, `notice`다. 이 이름들과 입력 dict의 키가 대응해야 한다. 값으로 넘긴 문자열이 Python 소스 코드로 실행되는 것은 아니다.

```python
data = {
    "audience": "신입사원",
    "tone": "정중하고 간단하게",
    "notice": "11월 20일 14시, 3층 교육장. 노트북 지참.",
}
print(sorted(prompt.input_variables))
value = prompt.invoke(data)
```

출력 변수 목록은 `['audience', 'notice', 'tone']`이다. 알파벳 정렬 순서는 메시지 출력 순서와 다른 개념이다.

### 2.2 역할·지시·맥락은 서로 다른 구분이다

`system`과 `human`은 메시지 역할이다. ‘사실만 사용하라’는 지시이고, ‘11월 20일 14시’는 이번 작업에 필요한 맥락이다. 지시·맥락은 내용의 기능이므로 역할 이름과 일대일 대응하지 않는다. human 메시지에도 ‘세 줄로 써 달라’는 지시가 들어갈 수 있다.

오늘은 유지하기 쉬운 구조를 위해 고정 업무 규칙을 system에, 매 요청의 값을 human에 둔다. 입력 문서를 system 메시지로 올린다고 신뢰할 수 있는 정보가 되는 것은 아니다. 역할 분리는 중요하지만 프롬프트 주입을 완전히 막는 보안 장치는 아니다.

### 2.3 템플릿이 검증해 주는 것과 우리가 검증할 것

필수 변수 누락은 템플릿 렌더링에서 발견할 수 있다. 그러나 `notice="   "`가 업무상 유효한 공지인지는 별도로 판단해야 한다. 템플릿은 `notice`가 충분한 사실을 담았는지, 길이가 적절한지, 권한이 있는 정보인지까지 보장하지 않는다.

| 조건 | 확인 주체 | 예 |
| --- | --- | --- |
| 변수 이름 누락 | 템플릿 | `tone` 키 없음 |
| 비어 있지 않은 문자열 | Python 검증 함수 | 공백 공지 거절 |
| 사실의 충분성 | 업무 규칙·사용자 확인 | 날짜 미정 표시 |
| 생성된 내용의 정확성 | 출력 검토·평가 | 없는 장소를 만들었는지 확인 |

변수가 하나인 템플릿에는 단일 문자열을 전달할 수 있는 편의 기능도 있다. 오늘은 변수가 여러 개이고 입력 계약을 명확히 보여 주기 위해 dict 전달을 기본으로 사용한다.

### 2.4 partial은 일부 값을 먼저 채운 새 템플릿이다

외부 협력사용 안내문의 어조가 항상 같다면 `tone`을 미리 채울 수 있다.

```python
formal = prompt.partial(tone="격식 있게")
print(sorted(formal.input_variables))
value = formal.invoke({"audience": "협력사", "notice": "금요일까지 자료 제출"})
```

이 경우 남은 필수 변수는 `audience`, `notice`다. `partial`은 응답을 생성하거나 모델을 학습시키는 기능이 아니다. 값 일부가 채워진 새 프롬프트 객체를 반환한다. 원래 `prompt`는 계속 세 변수를 받을 수 있다.

중괄호를 문자 그대로 포함하려면 `{{`와 `}}`를 사용한다. 예를 들어 JSON 모양을 지시문에 적을 때는 `예: {{"title": "공지"}}`처럼 쓴다. 단순한 JSON 모양의 지시가 스키마 준수를 보장하지는 않는다. 구조화 출력은 이후 항목에서 별도로 배운다.

## 3교시. LCEL은 데이터 흐름의 선언이다

### 3.1 Runnable과 파이프

Runnable은 입력을 받아 출력을 내는 LangChain 구성 요소의 공통 실행 인터페이스다. 프롬프트, 모델, 파서는 모두 `invoke`로 실행할 수 있다. 이 객체들을 `|`로 연결하면 왼쪽 출력이 오른쪽 입력으로 전달되는 순차 체인을 만든다. 이 표현 방식을 LCEL, LangChain Expression Language라고 부른다.

```python
chain = prompt | model | StrOutputParser()
answer = chain.invoke(data)
```

여기서 `|`는 이 객체들이 정의한 결합 연산이다. 문자열끼리 파이프를 쓰는 것도 아니고, 운영체제 셸 명령을 실행하는 것도 아니다. 연결만 해서는 API가 호출되지 않는다. 실제 `invoke` 또는 `batch` 같은 실행 메서드를 부를 때 동작한다.

### 3.2 중간 타입을 먼저 적어야 하는 이유

| 단계 | 입력 | 출력 | 원격 호출 |
| --- | --- | --- | --- |
| `prompt` | `dict` | `ChatPromptValue` | 없음 |
| `model` | `ChatPromptValue` 등 지원 입력 | `AIMessage` | 실제 모드에서 발생 |
| `StrOutputParser()` | 텍스트 메시지 등 | `str` | 없음 |

다음 단계가 받을 수 없는 타입을 연결하면 체인이 실패한다. 문자열로 끝난 체인 뒤에 `{draft}`라는 dict 입력을 기대하는 새 템플릿을 바로 붙여도 문자열이 자동으로 `draft` 키에 매핑되는 것은 아니다. 변수가 하나인 프롬프트의 편의 기능에 기대기보다 명시적으로 dict를 만들어 주는 것이 데이터 흐름을 설명하기 쉽다.

### 3.3 단계별 코드와 LCEL 코드의 관계

```python
value = prompt.invoke(data)
response = model.invoke(value)
answer = parser.invoke(response)
```

이 세 단계를 `prompt | model | parser`로 연결할 수 있다. 단계별 코드는 중간 결과를 관찰하기 쉽고, LCEL은 전체 흐름을 재사용하기 쉽다. 동작을 비교하기 위해 둘 다 실행하면 모델을 두 번 호출한다. 3교시 예제가 실제로 2회 호출하는 이유다. 두 응답 문장이 달라져도 즉시 버그라고 단정하지 않는다.

`StrOutputParser`는 오늘의 텍스트 응답을 문자열로 다루기 쉽게 만든다. 사실 확인·문장 교정·업무 규칙 검사·JSON 스키마 검증을 수행하는 기능은 아니다. 출력이 `str`라는 사실과 내용이 올바르다는 판단을 나누어야 한다.

설치한 버전의 내부 구현에 따라 출력 클래스 이름이 `TextAccessor`처럼 보일 수 있다. `str`의 하위 클래스이므로 이 수업에서는 `isinstance(answer, str)`로 문자열 계약을 확인한다. 3교시 예제는 클래스 이름을 외우는 대신 `str 호환: True`를 출력한다.

### 3.4 입력 하나를 바꾼다는 것

동일한 체인에 다른 `audience` 값을 넣으면 템플릿과 모델 연결은 재사용하고 요청 값만 바뀐다. 그러나 체인이 이전 실행의 값을 자동으로 기억하는 것은 아니다. 오늘의 체인은 상태를 저장하지 않으며 각 요청에 필요한 값을 다시 전달한다.

3교시가 끝나면 `dict → ChatPromptValue → AIMessage → str`를 직접 적고, 모델을 지나지 않은 출력과 모델을 지난 출력을 구분할 수 있어야 한다.

## 4교시. 좋은 프롬프트는 비교 가능한 요구사항을 가진다

### 4.1 기준선이 필요한 이유

‘B 프롬프트가 더 좋아 보인다’는 감상만으로는 무엇이 좋아졌는지 알 수 없다. 오늘 업무에서는 **제공 사실 준수, 출력 형식, 행동 안내**를 분리해 평가한다. 기준선 A는 독자·어조·사실을 전달하고 안내문 작성을 요청한다. 개선안 B는 동일한 값에 ‘없는 사실을 만들지 않기, 미정 항목 표시, 제목·핵심·행동 형식’을 추가한다.

A와 B는 같은 사례와 같은 모델로 비교한다. 이번 실험은 규칙을 묶어서 추가한 프롬프트 구성의 효과를 관찰한다. 여러 규칙을 동시에 바꾸었으므로 어느 한 문장만의 인과 효과를 밝혔다는 결론은 낼 수 없다.

### 4.2 생성 전에 성공 기준을 정한다

| 기준 | 0점 | 1점 | 2점 |
| --- | --- | --- | --- |
| 사실 준수 | 원문에 없는 핵심 사실을 단정 | 일부 누락·모호한 표현, 핵심 허구는 없음 | 핵심 사실 유지, 미정 항목을 지어내지 않음 |
| 형식 준수 | 지정된 항목 거의 없음 | 세 항목 중 일부만 충족 | 제목·핵심·행동이 모두 구분됨 |
| 행동 명확성 | 잘못된 행동 요구·행동 없음 | 행동은 있으나 대상·기한 등이 모호 | 원문이 허용한 행동·기한을 명확히 안내 |

행동 점수는 원문에서 확인 가능한 범위로 채점한다. 제출 방법이 미정이라면 임의 이메일 주소를 쓰는 것은 감점이다. ‘담당자에게 방법을 확인’처럼 불확실성을 드러낸 행동은 인정할 수 있다. N02는 날짜가 미정이므로 완성된 날짜를 만들어 넣으면 사실 점수 0점이다.

### 4.3 통제할 것과 기록할 것

동일 공급자·모델 ID·입력 사례·출력 상한·temperature·평가기준을 유지한다. 각 사례에서 A/B 순서를 교차해 시간 순서 영향을 조금 줄인다. 호출별 성공/실패·경과 시간·usage·출력·평가 점수를 기록한다. 단 세 사례의 결과만으로 프롬프트의 보편적 우수성을 증명할 수는 없다.

`temperature=0`은 변동을 줄이는 설정이지 응답 문장을 완전히 고정하는 보장은 아니다. 같은 모델의 별칭이 나중에 다른 버전을 가리킬 수 있어 이번에는 날짜 고정 ID를 예시로 사용한다. 그래도 API 서비스 조건이나 비결정성까지 제거되지는 않는다.

### 4.4 품질·속도·실패율을 나누어 읽는다

기록 6건 중 실패가 있으면 실패를 지우지 않는다. 성공 응답에만 품질 점수를 주되 성공 건수와 실패 건수를 함께 보고한다. 시간 측정은 요청 직전부터 응답 처리까지의 경과 시간이며 네트워크와 클라이언트 오버헤드를 포함한다. 모델만의 순수 추론 시간이라고 쓰지 않는다. 6건으로 p95 성능 우열을 주장하지 않는다.

모의 모델은 항상 같은 합성 응답이므로 A와 B의 지시를 따르는 능력을 측정하지 않는다. 모의 실행의 목적은 JSON 기록 구조·사례 매칭·오류 기록을 점검하는 것이다. 실제 API를 실행하지 못했다면 비교 점수를 채우지 않고 ‘원격 미실행’으로 남긴다.

### 4.5 Groq는 무엇을 비교하게 하는가?

OpenAI 모델과 Groq에서 제공하는 다른 모델을 비교하면 공급자·모델 구성이 함께 바뀐다. 이를 ‘Groq라는 공급자만의 효과’나 ‘프롬프트만의 효과’라고 표현하지 않는다. 이번 필수 A/B 비교는 OpenAI 안에서 완료하고, Groq는 7교시 선택 반복에 사용한다.

## 5교시. 오류 위치를 좁히는 방법

### 5.1 모델을 의심하기 전에 입력을 본다

오류는 설치, 입력 검증, 템플릿 렌더링, 모델 요청, 출력 처리 중 어느 단계에서도 발생할 수 있다. 가장 먼저 실패한 단계를 좁혀야 한다. 공지 내용이 비어 있는 문제를 모델 교체로 해결하려 하면 호출 비용만 늘어난다.

오늘 입력 계약은 다음과 같다.

| 키 | 타입 | 허용 범위 | 정리 방식 |
| --- | --- | --- | --- |
| audience | str | 공백이 아니며 최대 80자 | 양끝 공백 제거 |
| tone | str | 공백이 아니며 최대 80자 | 양끝 공백 제거 |
| notice | str | 공백이 아니며 최대 1,200자 | 양끝 공백 제거 |

길이 상한은 이번 수업의 설계값이며 API의 최대 컨텍스트 길이가 아니다. 검증 함수는 입력에 있던 다른 키를 반환하지 않는다. 뒤에서 요청 ID를 유지하려면 그 키에 대한 검증과 보존을 별도로 설계해야 한다.

### 5.2 왜 검증 함수를 체인 맨 앞에 두는가?

```python
def validate_input(data):
    value = data.get("notice")
    if not isinstance(value, str) or not value.strip():
        raise ValueError("notice: 비어 있지 않은 문자열이 필요합니다.")
    return data
```

이 작은 예시는 핵심 판단만 보여 준다. 실제 공통 함수는 세 필드와 길이를 모두 확인하고 정리한 새 dict를 반환한다. `RunnableLambda(validate_input)`으로 감싸면 LCEL 맨 앞에 넣을 수 있다. 잘못된 입력은 모델 앞에서 종료되므로 불필요한 호출을 줄일 수 있다.

과거 Pydantic 학습과 연결하면, 같은 입력 계약을 모델 클래스로 표현할 수도 있다. 오늘은 함수와 Runnable의 연결이 핵심이므로 수동 검증 함수를 사용한다. LangChain이 모든 업무 검증을 자동으로 수행한다는 뜻은 아니다.

### 5.3 세 종류의 재현

- **키 누락:** `prompt.invoke({"notice":"점검"})`는 다른 필수 변수가 없어서 실패한다. 모델 호출 이전 실패다.
- **유효하지 않은 값:** 키가 있어도 `notice="  "` 또는 `notice=123`은 업무 입력 규칙을 위반한다.
- **리터럴 중괄호:** JSON 예시의 `{}`가 변수 표기로 해석되면 의도하지 않은 변수가 생긴다. 템플릿 문자열의 중괄호를 이스케이프한다.

5교시 예제는 앞의 오류를 격리해서 관찰하고 오류 종류만 출력한다. 전체 키나 실제 입력 비밀값을 로그로 남기지 않는다. 이후 정상 입력을 넣어 수정이 다른 경로를 깨지 않았는지도 확인한다.

### 5.4 회귀 검증은 고친 예제 하나로 끝나지 않는다

‘공백 공지’를 고쳤다면 정상 공지, 다른 필드의 공백, 상한 초과 공지를 함께 확인한다. 오류가 사라졌다는 사실과 원인을 해결했다는 사실을 구분한다. 예외를 무조건 삼키고 빈 문자열을 반환하면 겉으로 실행은 끝나도 실패를 감춘 것이다.

API 인증·한도 오류는 로컬 입력 오류와 처리 방법이 다르다. 키를 바꾸기 전에 오류 코드와 공급자를 확인하고, 잘못된 키를 반복 호출하지 않는다. 오늘 기본 코드는 키를 노출하지 않는 안내문을 출력하고 종료 코드 1로 끝난다.

## 6교시. 원문을 보존하며 두 체인을 통합한다

### 6.1 문자열 출력만 남기면 어떤 정보가 사라지는가?

`prompt | model | parser`의 출력은 문자열이다. 이 출력만 다음 검토 단계로 전달하면 독자·원문·어조가 사라진다. 검토 모델이 초안만 보고 원문 사실과 맞는지 확인하기는 어렵다. 데이터가 필요한 다음 단계까지 도달하도록 설계해야 한다.

검토 단계 입력은 최소한 `notice`와 `draft`를 포함하는 dict여야 한다. 단순 문자열을 dict로 포장하는 것은 `RunnableLambda`로 할 수 있지만, 이미 사라진 원문은 저절로 되살아나지 않는다. 따라서 입력을 유지하면서 결과를 추가하는 구성이 필요하다.

### 6.2 RunnableLambda

`RunnableLambda`는 Python 함수를 Runnable로 사용할 수 있게 감싼다. 함수가 무엇을 입력받고 무엇을 반환하는지는 여전히 작성자가 책임진다.

```python
normalize = RunnableLambda(validate_input)
```

이 객체는 입력 dict를 검증·정리한 dict로 바꾼다. 함수를 감쌌다고 그 안에서 실행하는 작업이 자동으로 스트리밍되는 것은 아니다. 전체 입력을 기다리는 함수가 있으면 스트리밍 전달이 그 지점에서 묶일 수 있다.

### 6.3 RunnablePassthrough.assign

`assign`은 입력 dict의 기존 키를 유지하면서 지정한 새 키의 값을 계산한다.

```python
with_draft = RunnablePassthrough.assign(draft=draft_chain)
```

`draft_chain`은 같은 입력 dict를 받아 실행되고, 결과가 `draft` 키에 들어간다. 원래의 `notice`는 그대로 남는다. `assign` 자체에 원문 복원 기능이 있는 것이 아니라, dict 입력을 유지하는 방식이 핵심이다.

| 위치 | 보유 키 | 모델 누적 호출 |
| --- | --- | ---: |
| 검증 직후 | audience, tone, notice | 0 |
| 첫 assign 뒤 | audience, tone, notice, draft | 1 |
| 둘째 assign 뒤 | audience, tone, notice, draft, review | 2 |

두 번째 `assign`에 연결된 검토 체인은 첫 번째 assign이 끝난 dict를 받는다. 따라서 `draft`를 읽을 수 있다. 같은 assign 호출 안에서 한 새 필드가 다른 새 필드의 계산 완료를 당연히 기다린다고 가정하면 안 된다. 의존 단계는 오늘처럼 순서대로 분리한다.

### 6.4 검토 체인은 정답 판정기가 아니다

검토 프롬프트는 원문과 초안의 차이를 지적하도록 요청한다. 검토 모델도 사실을 놓치거나 잘못된 지적을 할 수 있다. 원문을 보존하는 구조가 작동했는지와 검토 내용이 정확한지는 서로 다른 평가다. 사람은 원문에 없는 날짜·장소·제출처가 생겼는지 직접 확인한다.

이번 검토는 자동 수정·무한 재생성 루프를 포함하지 않는다. 초안 생성 1회와 검토 1회로 종료한다. 호출 횟수를 예측할 수 있는 고정 순차 체인이다.

## 7교시. 여러 입력 처리와 점진적 독립

### 7.1 invoke와 batch

`invoke`는 한 입력에 대한 실행이다. `batch`는 입력 목록을 처리해 결과 목록을 반환한다. 결과 목록의 순서는 입력 순서와 대응한다. 내부 실행이 반드시 하나씩 이루어지는 것은 아니므로 수업에서는 동시성 상한을 1로 둔다.

```python
outputs = chain.batch(inputs, config={"max_concurrency": 1})
```

입력 2개를 처리하는 것은 일반적으로 모델 요청도 2회라는 뜻이다. 한 번의 저렴한 공급자 Batch API 요청으로 자동 전환된다고 생각하면 안 된다. LangChain의 `batch` 메서드와 공급자가 운영하는 별도 Batch API는 구분한다.

`max_concurrency=1`은 동시 요청을 줄일 뿐 분당 호출량을 자동 조절하는 속도 제한기는 아니다. 조직의 요청·토큰 한도에 따라 요청 사이 간격도 조정해야 할 수 있다. 입력이 많아질수록 성공·실패를 개별 요청과 연결할 ID도 필요해진다.

### 7.2 stream은 선택 실습

`stream`은 출력 조각을 순서대로 받아 처리한다. 지원 모델과 체인 구성에서는 사용자가 전체 응답을 기다리기 전에 일부 텍스트를 볼 수 있다.

```python
for chunk in chain.stream(data):
    print(chunk, end="", flush=True)
```

조각 하나가 문장 하나라는 보장은 없다. 조각을 합친 결과의 전체 형식은 생성이 끝난 뒤 확인한다. 스트리밍을 추가 실행하면 모델 요청도 하나 늘어난다. 모의 모델은 고정 문자열 전체를 한 번에 내보낼 수 있으므로 실제 토큰 전달 성능을 검증하지 않는다.

중간 Runnable이 출력 전체를 받아야 일하는 함수라면 스트리밍이 그 지점에서 지연될 수 있다. 오늘의 입력 검증은 모델 앞에 있어 입력 전체를 먼저 확인하고, 그 다음 생성 단계가 진행된다.

### 7.3 공급자 교체의 책임 경계

체인은 공통 모델 인터페이스에 연결되어 있으므로 팩토리에서 모델 객체를 바꿀 수 있다. OpenAI는 `ChatOpenAI`, Groq는 `ChatGroq`를 사용한다. OpenAI 키를 Groq에 넘기거나 OpenAI 모델 ID를 그대로 Groq 모델 ID로 쓰지 않는다. `openai/gpt-oss-20b`처럼 Groq 목록에 있는 ID는 Groq 설정으로 사용한다.

여기서 재사용하는 것은 오늘의 텍스트 채팅 입출력이다. 도구 호출·구조화 출력·특정 파라미터까지 동일하게 동작한다는 보장은 없다. 오늘의 비교를 뒤의 모든 기능으로 확대하지 않는다.

### 7.4 독립 구현이 필요한 이유

7교시에는 `build_batch_chain(model)`의 요구사항만 보고 입력 검증·템플릿·모델·파서를 직접 연결한다. 먼저 입력·출력 타입을 적고, 한 입력을 통과시킨 뒤 두 입력 배치로 넓힌다. 해설을 보기 전에 모의 실행으로 구조를 확인한다.

연습 중 AI에게 오류 설명을 요청할 수 있지만, 종료 전 5분 확인은 AI와 해설 없이 새 템플릿의 변수·타입·호출 수를 설명한다. AI를 활용한 코드 완성과 자신의 설명 능력을 별도로 남긴다.

## 8교시. 요구사항으로부터 서비스 로직을 설계한다

### 8.1 출력에서 거꾸로 설계하기

마지막 요구사항은 ‘안내문 문자열을 반환한다’에서 확장된다. 요청과 결과를 연결하려면 **request_id와 원문도 함께 반환**해야 한다.

```python
# 입력
{
    "request_id": "R08",
    "audience": "신규 협력사",
    "tone": "격식 있게",
    "notice": "자료 제출 기한은 미정입니다. 담당자에게 확인하세요.",
}
# 출력의 형태
{
    "request_id": "R08",
    "notice": "자료 제출 기한은 미정입니다. 담당자에게 확인하세요.",
    "answer": "생성된 안내문 문자열",
}
```

`request_id`는 Python 프로그램이 보존한다. 모델이 생성하도록 시키지 않는다. 이렇게 하면 안내문 내용이 달라도 어떤 요청의 응답인지 확실하게 대응시킬 수 있다. 모델 출력에서 ID를 다시 추출하는 불필요한 작업도 줄일 수 있다.

### 8.2 입력 검증과 출력 투영

일반 공지 검증 함수는 세 필드만 반환하므로 요청 ID가 사라질 수 있다. 종합 과제에서는 ID의 타입·공백·길이를 확인하고 정리된 dict에 함께 남겨야 한다. 이후 `answer`를 추가하고 마지막에 필요한 세 키만 선택한다.

| 설계 단계 | 질문 |
| --- | --- |
| 입력 검증 | 잘못된 ID·공백 공지가 모델 호출 전에 거절되는가? |
| 값 보존 | 정리된 원문과 ID가 모델 결과와 섞이지 않고 유지되는가? |
| 답변 생성 | 안내문은 기존 체인 인터페이스를 재사용하는가? |
| 출력 선택 | 필요한 키 세 개와 문자열 응답을 반환하는가? |

출력 키를 Python에서 고정하는 것은 응답 envelope를 만드는 일이다. 모델이 만든 안내문 내부의 모든 문장이 사실이라는 보장은 아니다. 요청 계약 검증과 문장 품질 평가는 둘 다 필요하다.

### 8.3 성공 증거를 분리한다

- **기능 증거:** 정상 입력에서 요청 ID·원문·답변이 나온다.
- **경계 증거:** 공백 공지·빈 ID·정수가 들어간 ID를 모델 호출 전에 거절한다.
- **설명 증거:** 각 단계의 입출력 타입과 원문 보존 위치를 말한다.
- **전이 증거:** `tone`을 미리 고정한 새 요구사항에서 남은 입력 계약을 다시 정한다.

자동 테스트를 통과했어도 해설을 그대로 복사했다면 독립 설계 능력까지 입증된 것은 아니다. 반대로 실제 API를 사용할 수 없는 날에는 구조·검증·설명은 평가할 수 있지만 생성 품질은 미실행으로 남겨야 한다.

### 8.4 다음 수업으로 넘길 인터페이스

다음 항목에서 바꾸는 중심은 프롬프트의 문제 해결 방식이다. 오늘 만든 입력 dict, 렌더링 단계, 모델 팩토리, 문자열 반환 계약은 재사용할 수 있다. 문제 분해나 간결한 검증 요약을 요구하는 프롬프트를 만들더라도, 출력 설명을 모델의 비공개 내부 사고 과정이라고 단정하지 않는다.

다음 수업 시작에는 자료 없이 다음을 회상한다. ‘`prompt.invoke`와 `chain.invoke` 중 어느 단계에서 비용이 발생하는가?’, ‘문자열 뒤에 원문이 필요한 템플릿을 붙이려면 무엇을 보존해야 하는가?’, ‘프롬프트 A/B 비교에서 고정해야 할 조건은 무엇인가?’
