# 요구사항 및 유스케이스

## 1. 목적

여행자가 지역과 날짜를 자연어로 입력하면, 가상 숙소·날씨와 Google Maps 정보를 활용해 이동 가능한 관광 일정을 추천한다. 답변은 시뮬레이션 여부, 후보 비교 근거, 정보 출처, 조회 시각과 함께 제공한다.

## 2. 이해관계자와 사용자

| 구분 | 관심사 |
|---|---|
| 여행자 | 예산·동행자·관심사에 맞는 실행 가능한 코스와 정보 출처 |
| 서비스 운영자 | API 비용·장애·데이터 품질·개인정보 및 비밀정보 관리 |
| 데이터/API 제공자 | 허용된 조회량, 이용 약관, 출처 표기, 데이터 최신성 |

## 3. 범위

### MVP 포함

- 대상 지역은 서울 광화문 권역으로 고정한다.
- 한국어 자연어 질문에서 목적지, 여행 날짜, 인원, 예산, 선호를 추출한다.
- 필수 정보가 부족하거나 지역이 모호하면 도구를 호출하기 전에 확인 질문을 한다.
- 가상 숙소 데이터에서 인원·날짜·가격 조건에 맞는 후보를 조회한다.
- 가상 날씨 시나리오에서 여행 날짜의 날씨 조건을 조회한다. 응답에 시뮬레이션임을 표시한다.
- Google Maps Platform을 통해 장소/경로 정보를 조회하고 일정 순서를 구성한다. 테스트에서는 Google Maps adapter mock을 사용한다.
- 추천은 hard constraint를 통과한 후보 중 숙박 총액이 낮은 순으로 정렬한다. 동률은 Google Maps 이동 시간으로 해소한다. 150,000 KRW/실/박은 조정 가능한 제안 기본값이다.
- 후보의 적합도와 데이터 근거를 사용자에게 설명한다.
- 일부 제공자 장애 시 사용 가능한 정보만으로 부분 결과를 제시하고 누락을 알린다.
- 데이터 source의 시뮬레이션/실시간 여부를 구분해 표시한다.

### MVP 제외

- 숙소 예약, 결제, 취소 및 공급자 데이터 변경.
- 최초 MVP의 실숙소·실날씨 연동. 다만 interface는 향후 adapter 교체를 지원해야 한다.
- 실시간 예약 가능성을 보장하는 행위.
- 사용자의 민감정보·여행 프로필을 장기 저장하는 기능.
- 데이터 출처가 없는 실시간 날씨·가격·운영 시간의 생성.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 질문을 `TravelIntent`로 변환한다: 지역, 날짜/기간, 인원, 예산, 관심사, 이동 제약 | Must |
| FR-02 | 날짜는 요청자의 시간대(기본 `Asia/Seoul`)로 해석한다. “오늘/내일”의 기준 날짜를 결과에 기록한다. | Must |
| FR-03 | 필수 슬롯이 없거나 여러 지역으로 해석되면 추측하지 않고 확인 질문을 한다. | Must |
| FR-04 | 가상 숙소 조회는 입력된 일정·인원·예산에 맞는 후보와 가상 가격·위치·`simulated` 출처를 반환한다. | Must |
| FR-05 | 가상 날씨 조회는 시나리오의 날씨·강수 정보를 반환하고 `simulated`임을 표시한다. | Must |
| FR-06 | Google Maps 장소/경로 조회 결과를 이용해 날짜·시간대별 순서를 구성한다. 이동 시간 또는 경로 근거가 없으면 이동 시간을 단정하지 않는다. | Must |
| FR-07 | ReAct Agent는 등록된 읽기 전용 도구 중 필요한 도구를 선택하고, 도구 반환값을 다음 호출의 관찰로 사용한다. | Must |
| FR-08 | 수용 인원·지역 등 hard constraint 적용 후 예산 상한 내 후보를 숙박 총액 오름차순으로 정렬한다. 동률은 Google Maps 경로 시간으로 해소하고 정렬 근거를 노출한다. | Must |
| FR-09 | 각 핵심 사실에 출처와 조회 시각을 연결한다. 가상 숙소/날씨는 `simulated`라고 표시하고 Google Maps 결과와 혼동하지 않는다. | Must |
| FR-10 | API 실패·타임아웃·빈 결과가 있어도 실패한 정보를 지어내지 않고 부분 결과와 한계를 설명한다. | Must |
| FR-11 | 한 요청당 도구 호출 수, 재시도 수, 토큰/시간 예산을 제한한다. | Should |
| FR-12 | 예약·결제 등 쓰기 도구는 MVP Agent에 등록하지 않는다. | Must |

## 5. 핵심 유스케이스

### UC-01: 여행 일정 추천

**주 액터:** 여행자  
**시작 조건:** 사용자가 여행지와 날짜를 묻는다.

1. 사용자가 “내일 광화문을 여행해요. 2명, 1박, 숙소는 1박 15만 원 이하로 추천하고 비 예보를 고려한 코스를 짜줘.”라고 입력한다.
2. Intent Parser가 지역·날짜·인원·숙박 수·예산·날씨 조건을 구조화한다.
3. 광화문 권역과 필수 값을 검증한다. MVP 날씨는 시뮬레이션임을 유지한다.
4. Agent가 가상 숙소·날씨와 Google Maps 장소·경로 도구를 필요한 순서로 호출한다.
5. 각 도구 결과를 검증하고 출처/시간과 함께 Evidence Set에 저장한다.
6. Ranker가 인원·지역 조건 위반과 1박 150,000원 초과 숙소를 제외하고, 남은 후보를 숙박 총액 오름차순으로 정렬한다.
7. Response Composer가 일정, 추천 이유, 날씨 대안, 숙소 후보, 출처와 데이터 시각을 반환한다.

**예외 흐름**

- 지역이 모호함: 지역을 먼저 확인한다.
- 날짜/인원/예산 누락: 일정 추천에 필요한 최소 정보만 질문한다. 합리적인 기본값을 쓰는 경우 답변에 명시한다.
- 숙소/날씨 fixture 누락 또는 손상: 정상 조회된 근거만 이용한 부분 결과를 표시한다.
- Google Maps 조회 실패: 경로 정보를 추측하지 않고 누락을 알린다. 다른 근거도 없으면 재시도 가능한 안내를 반환한다.

## 6. 초기 비기능 요구사항(제안)

수치는 데이터 공급자와 모델을 선정한 뒤 부하·비용 테스트로 확정한다.

| 항목 | 초기 목표 |
|---|---|
| 응답시간 | Google Maps와 모델이 정상인 조건에서 전체 요청 p95 20초 이내(제안) |
| 외부 호출 | 공급자별 timeout 설정, 제한된 재시도(최대 1회), 전체 시간 예산 준수 |
| 정확성 | 날짜·통화·인원 단위가 보존되고, 출처 없는 사실을 실시간 사실처럼 제시하지 않음 |
| 가용성 | 부분 장애 시 성공한 소스의 결과를 유지하며 실패 데이터와 구분 |
| 보안 | API 키는 Secret Manager/환경변수에 보관, 로그·프롬프트에 비밀정보 미포함 |
| 관측성 | 요청 ID, 도구명, 상태, latency, 데이터 시각, 오류 코드를 추적 |
| 비용 | 사용자 요청당 Agent step·토큰·API 호출 상한 설정 |
| 접근성 | 결과는 텍스트로 이해 가능하고 표/링크는 보조 표현으로 제공 |

## 7. 인수 기준

- “오늘”은 설정된 시간대의 날짜로 해석되며, 해석된 날짜가 로그와 답변에 확인 가능하다.
- 필수 입력 누락 또는 지역 모호성에서는 외부 검색을 시작하지 않고 확인 질문을 한다.
- 숙소·날씨·경로의 성공/실패가 각각 구분되고, 성공 결과에는 출처와 시각이 있다.
- 가상 숙소/날씨는 모든 화면에서 시뮬레이션임을 알리고, Google Maps 데이터와 구분한다.
- Agent가 미등록 도구명이나 잘못된 인자를 요청하면 실행 전에 거부한다.
- 제안 기본 예산 150,000 KRW/실/박(설정 가능)보다 비싼 숙소는 기본 추천에 들지 않으며, 적격 후보는 숙박 총액이 낮은 순으로 정렬된다.
- Google Maps 경로가 없을 때 이동 시간을 만들어내지 않고 정보 부족을 알린다.
- 예약·결제 호출 경로가 존재하지 않는다.
