CoT·ReAct 프롬프트 작성 실습

생성형 AI API의 단계적 처리 관찰

2026년 11월 18일 · U2-02 · 이규영 강사 · 8차시

전날의 ChatPromptTemplate·LCEL을 이용해 같은 수학 문장제를 세 방식으로 처리한다. 정답만 요청하는 방식, 핵심 계산식과 짧은 풀이를 요청하는 방식, 계산 도구의 결과를 받아 다음 행동을 결정하는 ReAct 방식이다. 관찰 대상은 공개 응답, 프로그램이 실행한 계산, 메시지의 변화다. 이를 모델의 비공개 내부 사고를 직접 관찰한 기록으로 부르지 않는다.

수업 데이터 근거: 사용자가 제공한 캠프 데이터 목록의 D04 GSM8K. 원본은 openai/gsm8k → main 설정 → test 분할 → 0~5번 행이다. question과 answer를 그대로 보존하고 출처 확인용 필드를 덧붙였다. 원본에는 문제별 ID 필드가 없으므로 gsm8k-main-test-0000처럼 분할·행 번호로 수업용 ID를 만들었다. 이 표본은 6개이며 GSM8K 전체 성능을 측정하는 벤치마크가 아니다.

차시당 50분, 총 400분은 시간표가 별도로 없을 때의 설계 가정이며 휴식은 별도다. Python 함수·dict/list·예외 처리와 전날 템플릿을 재사용하되 필요한 부분을 다시 설명한다. 내일의 Structured Output·Pydantic, 이후의 native Tool Calling·LangGraph는 선수 조건으로 요구하지 않는다. 오늘은 텍스트 규약을 해석하는 작은 Python 반복문으로 원리를 드러낸다.

시작 환경

Python 3.11 이상에서 실행한다. 아래 명령은 ZIP을 푼 CoT_ReAct_20261118 폴더에서 Windows CMD를 사용하는 예다. Python 3.12 환경에서 제작·로컬 검증했다.

py -3.12 -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
copy .env.example .env
python main.py --session 1

PowerShell에서 활성화가 제한되면 .\.venv\Scripts\python.exe main.py --session 1처럼 Python을 직접 실행한다. macOS/Linux는 python3 -m venv .venv, source .venv/bin/activate 후 같은 python 명령을 사용한다.

app은 ZIP에 포함된 자체 패키지다. pip install app을 실행하지 않는다. main.py가 있는 루트에서 실행하면 app/core.py, app/providers.py, app/report.py를 가져온다. 설치 대상은 langchain-core와 python-dotenv 두 직접 의존성이다. 세 공급자의 HTTP 요청은 Python 표준 라이브러리로 작성하여 선택하지 않은 SDK까지 설치하지 않는다.

실제 API를 쓸 때는 .env에서 선택한 공급자의 키와 모델 ID만 채운다. Gemini는 models/ 접두어 없이 모델 코드만 사용한다. 모델 ID는 제공 계정의 모델 목록에서 사용 가능한 채팅/텍스트 모델을 선택한다. 예제에 모델 이름을 고정해 계정 권한을 가정하지 않는다.

LLM_PROVIDER=groq
GROQ_API_KEY=여기에_발급받은_키
GROQ_MODEL=계정에서_사용가능한_모델_ID

gemini이면 GEMINI_API_KEY, GEMINI_MODEL, openai이면 OPENAI_API_KEY, OPENAI_MODEL을 채운다. 키는 결과 파일과 화면에 넣지 않는다. OpenAI는 유료 호출 경로다. Groq·Gemini도 선택한 계정/프로젝트와 모델에서 무료인지 확인한다. Gemini 구독 여부만으로 API 무료 사용을 판단하지 않는다. 공급자 실패 시 자동 전환이나 자동 재시도는 하지 않는다.

기본 실행과 --mock은 교사 작성 대본 모델을 사용한다. 계산기는 실제로 동작하지만 모델 품질을 실험하는 실행은 아니다. --live를 붙여야 외부 API를 호출한다. 제작 시 실제 API 키를 사용한 원격 실행은 수행하지 않았으며, 세 공급자의 요청/응답 변환은 모의 HTTP로 검증했다.

1차시 · 데이터 원본과 모델 입력을 구분하기

같은 문제를 비교하려면 먼저 입력을 고정한다

쇼핑몰의 매출이나 재고 수량을 설명하는 서비스에서도 수량을 잘못 해석하면 계산이 맞아도 업무 답은 틀릴 수 있다. 오늘은 문제와 수치 정답이 함께 있는 GSM8K로 입력 해석·계산·결과 대조를 분리한다. 원본은 영어 문장제다. 한국어 풀이를 요청하더라도 숫자·질문 원문을 바꾸지 않아 같은 문제를 비교할 수 있게 한다.

예를 들어 원본 0번 행은 하루 16개 달걀 중 아침 식사에 3개, 머핀에 4개를 쓰고 나머지를 개당 2달러에 판매하는 문제다. 수업용 한국어 요약이며 원문 번역 필드를 새 원본으로 만들지 않는다. 남은 수량은 16-3-4=9, 매출은 9*2=18이다. 16개 전체에 2달러를 곱하면 계산식의 문법은 맞아도 문제 해석이 틀린다.

원본 위치 수업용 ID 확인할 수량 관계 원본 최종 답
main/test 0행 gsm8k-main-test-0000 남은 달걀 수 × 단가 18
main/test 1행 gsm8k-main-test-0001 파란 천 + 그 절반의 흰 천 3
main/test 2행 gsm8k-main-test-0002 가치 증가 후 매각가 − 전체 비용 70000
main/test 3행 gsm8k-main-test-0003 주당 횟수 × 회당 거리 540
main/test 4행 gsm8k-main-test-0004 하루 필요량 − 이미 준 양 20

행 번호는 0부터 센다. 파일의 여섯 항목은 원본 main/test의 처음 여섯 행이며 난이도 대표 표집이 아니다. 제공 목록의 다른 데이터나 임의 쇼핑몰 JSON을 사용한 것이 아니다.

작성 파일: app/core.py의 로더

Path(__file__).resolve().parents[1]은 app/core.py의 상위 프로젝트 폴더를 찾는다. 데이터 경로를 이 폴더에 붙여 실행 위치 때문에 엉뚱한 파일을 읽는 문제를 줄인다. 파일 내용은 JSON 문자열이며 json.loads가 이를 list[dict]로 바꾼다.

def load_records():
    records = json.loads((ROOT / 'data/gsm8k_sample.json').read_text(encoding='utf-8'))
    if not records:
        raise ValueError('데이터가 비어 있습니다.')
    for row in records:
        if not all(isinstance(row.get(k), str) and row[k] for k in ('id', 'question', 'answer')):
            raise ValueError('id/question/answer 문자열이 필요합니다.')
    return records

records[0]은 첫 문제의 dict다. records[0]["question"]은 모델에 보낼 문자열이고 records[0]["answer"]는 실행 후 대조할 정답 설명이다. 로더는 필수 문자열이 있는지만 확인한다. 단위가 맞는지나 수학적으로 올바른지까지 자동 검증하는 함수는 아니다. 빈 배열과 필수 필드 누락은 ValueError로 일찍 알린다.

정답이 모델 입력에 섞이면 “문제를 풀었는가” 대신 “제공 정답을 복사했는가”를 비교하게 된다. 그래서 이후 모든 호출은 전체 row 대신 row["question"]만 넘긴다. 결과 저장 단계에서만 row를 다시 붙인다.

그림의 두 경로를 구분한다. question은 프롬프트를 거쳐 응답으로 이동하고, answer는 모델 호출을 건너뛰어 최종 대조 단계로 간다. data/provenance.json은 제공 데이터 ID·분할·행 번호·원본 필드·수업용 ID 생성 규칙을 담는다.

실행하고 원본 위치 확인

python main.py --session 1

터미널에 결과 HTML 경로가 나온다. 브라우저로 열면 원본 위치와 문제 원문이 표시된다. 상태는 local_only, 공급자와 모델은 none이다. API 호출은 발생하지 않는다. --id gsm8k-main-test-0003을 붙이면 같은 표본 안에서 선택 문제를 바꾼다.

FileNotFoundError가 나면 ZIP의 data/gsm8k_sample.json이 빠지지 않았는지 확인한다. 표본에 없는 ID는 명령행 오류로 종료한다. 결과 화면에 데이터 위치·행 번호·원문이 함께 보이는 부분을 캡처할 수 있다. 다음 차시에는 같은 question을 세 종류의 프롬프트에 넣는다.

2차시 · CoT의 원리와 짧은 풀이 프롬프트 작성

설명이 길다고 계산이 정확해지는 것은 아니다

CoT는 중간 계산이나 문제 분해의 예시를 프롬프트에 넣어 다단계 문제 해결을 유도하는 접근이다. few-shot CoT에서는 비슷한 문제의 계산 근거와 답을 함께 보여준다. zero-shot 방식에서는 예시 없이 풀이 구조를 요청한다. 오늘은 이 차이를 “정답만”, “핵심 계산과 짧은 검증”, “교사 작성 계산 예시 포함”으로 구현한다.

모델이 출력한 풀이는 사용자를 위한 설명이다. 설명이 실제 내부 계산을 충실하게 반영한다고 보장할 수 없고, 현대 추론 모델은 별도 지시 없이도 내부 추론을 사용할 수 있다. 그러므로 비공개 사고 전문 대신 계산식·단위·짧은 검증 요약·최종 숫자를 요청하고, 맞는지는 별도로 확인한다. 어떤 모델에서든 CoT가 반드시 더 좋아진다는 결론도 내리지 않는다.

전략 값 요청할 출력 비교할 점
direct 마지막 답 한 줄 간결하지만 틀린 이유를 화면만으로 알기 어려움
summary 계산식 1~3개와 검증 요약 수량 관계를 설명하지만 계산 정확성을 보장하지 않음
fewshot 다른 예시의 형식을 참고한 짧은 풀이 예시가 길이·문체·풀이 구조를 동시에 바꿀 수 있음

작성 파일: 프롬프트와 메시지 변환

def build_prompt(strategy):
    common = ('수학 문장제에 답하세요. 비공개 내부 사고를 요구하지 않습니다. '
              '사용자에게 필요한 계산식과 짧은 검증 요약만 보여주세요. '
              '최종 숫자는 마지막 줄에 #### 숫자 형식으로 쓰세요.')
    instructions = {
        'direct': '풀이 없이 마지막 답 한 줄만 쓰세요.',
        'summary': '문제의 수량과 단위를 확인하고 핵심 계산식 1~3개 및 한국어 검증 요약을 쓰세요.',
        'fewshot': ('아래 예시처럼 짧은 계산 근거와 답을 쓰세요. 예시는 교사 작성입니다.\n'
                    '예: 14개 중 4개를 쓰고 나머지를 3원씩 팔았다.\n'
                    '계산: (14-4)*3=30\n검증: 남은 10개에 개당 가격을 곱했다.\n#### 30'),
    }
    if strategy not in instructions:
        raise ValueError('알 수 없는 프롬프트 전략')
    return ChatPromptTemplate.from_messages([
        ('system', common + '\n' + instructions[strategy]), ('user', '{question}')
    ])

공통 지시문은 system 역할에, 원본 문제는 user 역할의 {question}에 둔다. strategy는 프롬프트를 고르는 Python 값이며 모델이 결정하지 않는다. instructions dict에서 선택한 문자열만 system에 붙인다. few-shot 예시는 교사가 별도로 만든 문제이므로 이번 비교 문제의 정답을 미리 넣지 않는다.

ChatPromptTemplate.from_messages는 아직 모델을 호출하지 않는다. .invoke({"question": ...})도 이 객체에서는 변수 채우기만 한다. 같은 이름의 invoke라도 호출 대상이 프롬프트인지 전체 체인인지에 따라 실행 범위가 다르다.

def to_messages(prompt_value):
    return [{'role': 'assistant' if m.type == 'ai' else 'user' if m.type == 'human' else m.type,
             'content': m.content} for m in prompt_value.to_messages()]

템플릿 결과의 메시지는 LangChain 객체다. HTTP API에 보내기 위해 role·content dict의 목록으로 바꾼다. human은 user, ai는 assistant로 바꾸며 system은 그대로 둔다. 반환형은 JSON으로 직렬화 가능한 list[dict]다. 모든 role을 user로 바꾸면 system 지시와 대화 이력을 잃는다.

모델 없이 렌더링 결과 비교

python main.py --session 2

화면에는 각 전략의 system·user 메시지가 실제 줄바꿈으로 표시된다. 같은 원본 문제가 세 번 나타나고 answer의 정답 설명 전체는 프롬프트에 없다. 교사 예시의 #### 30은 예시 답이며 대상 문제의 정답 필드를 넘긴 것이 아니다. 대상 문제에도 같은 수식을 기계적으로 적용하지 않도록 수량 관계를 읽는다.

변수명을 {questions}로 바꾸고 입력 dict는 question으로 유지하면 KeyError가 난다. 이는 API 장애가 아니라 템플릿 입력 이름 불일치다. 키를 일치시키면 해결된다. 전략 문구를 바꾼 뒤에는 2차시를 다시 실행해 실제 메시지에서 바뀐 부분을 확인한다.

다음 차시는 이 메시지를 실제 API 또는 모의 모델에 연결한다. 이때부터 체인 전체의 invoke는 모델 호출까지 진행한다.

3차시 · 비용을 고려한 세 공급자 호출과 LCEL 연결

같은 계약으로 보내고 공급자별 형식만 바꾼다

전날 LCEL의 |는 앞 단계 결과를 다음 단계 입력으로 넘겼다. 오늘은 ChatPromptTemplate → 메시지 목록 변환 → 채팅 호출로 연결한다. 공급자는 OpenAI·Groq·Gemini 중 하나를 선택하며 세 곳에 동시에 전송하지 않는다. 일반 텍스트 대화만 공통 계약으로 잡고 공급자 고유의 native tool/strict schema를 공통 지원한다고 가정하지 않는다.

반복은 현재 계정에서 무료 사용이 확인된 Groq 또는 Gemini를 우선한다. OpenAI는 유료 비교·기능 확인에 소수 호출로 선택한다. Gemini도 무료/유료 프로젝트와 모델에 따라 다르다. 화면에 키를 출력하지 않고, 실패한다고 다른 유료 API로 자동 전환하지 않는다.

app/providers.py: 설정과 요청 본문

아래 클래스의 세 부분을 순서대로 읽는다. __init__은 dotenv를 읽고 선택한 공급자의 키·모델을 확인한다. prepare는 URL·헤더·본문을 만들기만 하고 네트워크 요청은 하지 않는다. extract는 응답에서 공개 텍스트와 사용량을 꺼낸다. 마지막 __call__이 실제 HTTP 요청을 실행한다.

class RemoteChat:
    def __init__(self, provider, max_calls=8, max_tokens=800):
        load_dotenv(ROOT / '.env', override=False)
        if provider not in ('openai', 'groq', 'gemini'):
            raise ValueError('provider는 openai/groq/gemini 중 하나입니다.')
        self.provider = provider
        prefix = provider.upper()
        self.key = os.getenv(prefix + '_API_KEY', '').strip()
        self.model = os.getenv(prefix + '_MODEL', '').strip()
        if not self.key or not self.model:
            raise ValueError(f'{prefix}_API_KEY 와 {prefix}_MODEL 설정이 필요합니다.')
        if not 1 <= max_calls <= 30 or not 128 <= max_tokens <= 4096:
            raise ValueError('호출 상한 1~30, 출력 상한 128~4096을 사용하세요.')
        self.max_calls, self.max_tokens = max_calls, max_tokens
        self.calls = 0
        self.metrics = []

    def prepare(self, messages):
        if self.provider == 'gemini':
            system = '\n'.join(m['content'] for m in messages if m['role'] == 'system')
            contents = [{'role': 'model' if m['role'] == 'assistant' else 'user',
                         'parts': [{'text': m['content']}]} for m in messages if m['role'] != 'system']
            url = 'https://generativelanguage.googleapis.com/v1beta/models/'
            url += parse.quote(self.model, safe='') + ':generateContent'
            return url, {'x-goog-api-key': self.key}, {
                'systemInstruction': {'parts': [{'text': system}]}, 'contents': contents,
                'generationConfig': {'maxOutputTokens': self.max_tokens}}
        base = 'https://api.openai.com/v1' if self.provider == 'openai' else 'https://api.groq.com/openai/v1'
        return base + '/chat/completions', {'Authorization': 'Bearer ' + self.key}, {
            'model': self.model, 'messages': messages, 'max_completion_tokens': self.max_tokens}

    def extract(self, data):
        if self.provider == 'gemini':
            candidates = data.get('candidates', [])
            if not candidates or candidates[0].get('finishReason') != 'STOP':
                raise ValueError('Gemini 응답 거절·잘림·빈 후보')
            parts = candidates[0].get('content', {}).get('parts', [])
            text = ''.join(p.get('text', '') for p in parts if not p.get('thought', False))
            usage = data.get('usageMetadata', {})
        else:
            choices = data.get('choices', [])
            if not choices or choices[0].get('finish_reason') != 'stop':
                raise ValueError('응답 거절·잘림·빈 후보: 출력 상한/모델 지원을 확인하세요.')
            text = choices[0]['message'].get('content') or ''
            usage = data.get('usage', {})
        if not text.strip():
            raise ValueError('공개 응답 텍스트가 비어 있습니다.')
        return text, usage

    def __call__(self, messages):
        if self.calls >= self.max_calls:
            raise CallLimit('명령 단위 호출 상한 도달; 자동 공급자 전환 없음')
        self.calls += 1  # 실패 요청도 호출 예산에 포함한다.
        url, headers, payload = self.prepare(messages)
        req = request.Request(url, data=json.dumps(payload).encode('utf-8'),
                              headers={**headers, 'Content-Type': 'application/json'}, method='POST')
        started = time.perf_counter()
        try:
            with request.urlopen(req, timeout=45) as response:
                data = json.load(response)
            text, usage = self.extract(data)
        except error.HTTPError as exc:
            # 응답 본문·요청 헤더를 출력하지 않아 키 노출을 피한다.
            retry = exc.headers.get('Retry-After', '없음')
            raise RuntimeError(f'HTTP {exc.code}; Retry-After={retry}; 설정/한도 확인 후 수동 재실행') from None
        except (error.URLError, TimeoutError):
            raise RuntimeError('연결 실패 또는 45초 타임아웃; 자동 재시도 없음') from None
        self.metrics.append({'seconds': round(time.perf_counter() - started, 3), 'usage': usage})
        return text

provider.upper()로 groq를 GROQ로 바꿔 GROQ_API_KEY·GROQ_MODEL을 읽는다. 선택하지 않은 공급자의 키는 요구하지 않는다. .env의 override=False는 터미널에 이미 설정한 환경변수를 덮어쓰지 않는다는 뜻이다.

prepare의 OpenAI·Groq 분기는 messages를 그대로 사용한다. max_completion_tokens는 응답 생성 상한이며 모델별 지원을 확인해야 한다. Gemini는 system을 systemInstruction으로 분리하고 assistant role을 model로 바꾼 contents를 만든다. generationConfig.maxOutputTokens로 상한을 전달한다. API 키는 Gemini에서도 URL 쿼리가 아니라 헤더에 넣는다.

json.dumps(payload).encode("utf-8")는 Python dict를 HTTP 본문 바이트로 바꾼다. 서버의 JSON은 json.load(response)로 다시 dict가 된다. 여기서 직렬화된 문자열과 실제 응답 텍스트를 혼동하면 줄바꿈이 \n처럼 남을 수 있다. 결과 패널에는 extract가 꺼낸 문자열을 넣는다.

finish_reason=stop 또는 Gemini의 finishReason=STOP이 아니면 완성 답으로 쓰지 않는다. 길이 제한·거절·빈 응답을 구분해 확인할 수 있게 오류를 남긴다. Gemini의 thought=True 파트는 공개 답으로 취급하지 않는다. 다른 공급자에서도 별도 reasoning 필드를 읽거나 저장하지 않는다.

호출 수는 요청 직전에 증가하므로 실패도 예산에 포함된다. 기본 최대 8회, 출력 상한 800토큰, 요청 타임아웃 45초다. 자동 재시도는 0회다. 추론 토큰을 포함하는 모델에서는 800토큰이 부족해 공개 답이 잘릴 수 있다. 그때 모델 지원과 비용을 확인하고 --max-tokens 1600처럼 명시적으로 조정한다. 요청 수 상한은 계정의 금액 상한을 대신하지 않는다.

main.py: 공통 체인을 실행하기

def run_strategy(row, strategy, chat, max_turns):
    before = len(chat.metrics)
    try:
        if strategy == 'react':
            output = run_react(row['question'], chat, max_turns)
        else:
            chain = build_prompt(strategy) | RunnableLambda(to_messages) | RunnableLambda(chat)
            text = chain.invoke({'question': row['question']})
            output = {'status': 'finished', 'text': text, 'events': []}
    except (ValueError, RuntimeError, CallLimit) as exc:
        output = {'status': 'error', 'text': str(exc), 'events': []}
    return make_result(row, strategy, chat, output, chat.metrics[before:])

RunnableLambda(to_messages)는 프롬프트 결과를 HTTP 메시지 dict로 바꾸고, RunnableLambda(chat)은 선택한 채팅 객체를 호출한다. chain.invoke({"question": row["question"]})만 모델 입력으로 넘기므로 원본 answer는 요청에 들어가지 않는다. ReAct는 이 한 번짜리 체인 대신 다음 차시의 반복 함수를 호출한다.

before는 이번 전략 이전의 사용량 항목 수다. 실행 후 chat.metrics[before:]만 가져오므로 한 RemoteChat 객체를 여러 전략에서 재사용해도 각 전략의 실측 사용량을 구분할 수 있다. 네트워크/파싱 오류는 error 결과로 저장하며 성공처럼 정답 비교하지 않는다.

4차시 · ReAct의 Action 규약과 실제 계산기

도구 호출을 글로 쓰는 것과 실행하는 것은 다르다

ReAct는 다음 행동을 선택하고 실행 결과를 관찰하며 문제 해결을 이어가는 패턴이다. 계산 결과가 필요한 순간에 프로그램이 도구를 실행해 관찰값을 넣는다. 모델이 “계산 결과는 18이다”라고 쓴 문장은 실제 계산기 실행 증거가 아니다.

오늘의 간소화한 텍스트 규약은 아래와 같다. Plan은 다음 작업의 짧은 목적이며 비공개 내부 사고 전문이 아니다. native Function Calling API가 아니라 프로그램이 텍스트를 해석하는 교육용 프로토콜이다.

결과: 18

app/core.py: 허용된 식만 계산하기

가장 작은 고정 계산은 (16-3-4)*2다. 그러나 모델이 보내는 문자열을 실행하려면 허용 범위가 필요하다. eval(expression)은 함수 호출 같은 Python 코드까지 실행할 수 있으므로 사용하지 않는다. AST는 문자열을 구문 트리로 읽되 코드를 실행하지 않는다. 그 트리에서 숫자·사칙연산·단항 부호만 직접 처리한다.

def calculate(expression):
    # eval 없이 숫자와 + - * / 괄호만 계산한다.
    if not isinstance(expression, str) or len(expression) > 120:
        raise ValueError('계산식은 120자 이하 문자열이어야 합니다.')
    tree = ast.parse(expression.strip(), mode='eval')
    if len(list(ast.walk(tree))) > 48:
        raise ValueError('계산식이 너무 복잡합니다.')

    def visit(node):
        if isinstance(node, ast.Constant) and type(node.value) in (int, float):
            value = Decimal(str(node.value))
        elif isinstance(node, ast.UnaryOp) and isinstance(node.op, (ast.UAdd, ast.USub)):
            value = visit(node.operand) * (-1 if isinstance(node.op, ast.USub) else 1)
        elif isinstance(node, ast.BinOp) and isinstance(node.op, (ast.Add, ast.Sub, ast.Mult, ast.Div)):
            a, b = visit(node.left), visit(node.right)
            if isinstance(node.op, ast.Add): value = a + b
            elif isinstance(node.op, ast.Sub): value = a - b
            elif isinstance(node.op, ast.Mult): value = a * b
            else: value = a / b
        else:
            raise ValueError('숫자·사칙연산·괄호만 허용합니다.')
        if not value.is_finite() or abs(value) > Decimal('1e12'):
            raise ValueError('계산 범위를 벗어났습니다.')
        return value

    return format(visit(tree.body), 'f')

ast.parse(..., mode="eval")의 eval은 파싱 모드 이름이며 Python 내장 eval()을 호출하는 것이 아니다. tree.body부터 visit가 내려가며 값들을 계산한다. (16-3-4)*2의 맨 위는 곱셈이고 왼쪽은 뺄셈 트리다. 왼쪽이 9, 오른쪽이 2가 되면 마지막 곱셈이 18을 만든다.

검사/분기 처리 의미
최대 120자·AST 노드 48개 지나치게 큰 입력을 계산 전에 제한
Constant + int/float 숫자를 Decimal로 바꿈. bool은 제외
UnaryOp -3, +2 같은 부호 처리
BinOp + Add/Sub/Mult/Div 두 자식 값을 먼저 계산한 후 사칙연산
그 밖의 노드 함수 호출·변수·거듭제곱 등 거부
중간 결과 절댓값 1e12 초과 과도한 숫자를 제한

Decimal(str(node.value))로 0.1 같은 표본의 소수를 처리한다. 모든 실수 표현을 완전한 기호수학으로 계산하는 도구는 아니다. 반환은 JSON/메시지에 넣기 쉬운 숫자 문자열이다. 0으로 나누면 ArithmeticError 계열 예외가 난다. 여기서 오류가 났다고 0을 계산값으로 반환하지 않는다.

행동 형식도 검사하기

def parse_action(text):
    # 모델이 Observation을 작성하면 실제 도구 결과로 오인하지 않도록 거부한다.
    if re.search(r'^Observation\s*:', text, re.M):
        raise ValueError('Observation은 프로그램만 작성합니다.')
    if re.search(r'^####', text, re.M) and re.search(r'^Action(?: Input)?\s*:', text, re.M):
        raise ValueError('행동과 최종 답을 동시에 내면 안 됩니다.')
    if parse_final(text) is not None:
        return None
    names = re.findall(r'^Action:\s*([^\n]+)$', text, re.M)
    inputs = re.findall(r'^Action Input:\s*([^\n]+)$', text, re.M)
    if len(names) != 1 or len(inputs) != 1 or names[0].strip() != 'calculator':
        raise ValueError('Action: calculator 와 Action Input: 계산식 한 쌍이 필요합니다.')
    return inputs[0].strip()

정규식의 ^는 줄 시작이고 re.M은 여러 줄 각각의 시작을 검사한다. findall 결과가 한 쌍인지 검사하므로 Action을 두 개 써서 모호해진 응답을 실행하지 않는다. 허용 도구는 calculator 하나다. 모델이 직접 Observation을 쓴 경우도 거부하여 가짜 관찰이 실제 실행값처럼 보이지 않게 한다.

None은 “파싱 실패”가 아니라 정상적인 최종 답을 뜻한다. 이 반환 계약은 5차시 반복문에서 종료 분기로 사용된다. 파싱 실패는 ValueError로 구별한다.

5차시 · 행동·관찰·최종 답을 잇는 ReAct 반복문

대화 이력에 무엇을 추가하는가

한 번짜리 프롬프트는 응답을 받으면 끝나지만 ReAct는 모델 응답을 읽고 실행이 필요한지 결정한다. 계산이 필요하면 로컬 계산 결과를 대화에 추가해 모델을 다시 호출한다. 프로그램이 도구를 실행하는 책임과 모델이 다음 행동을 제안하는 책임을 나눈다.

run_react 안의 핵심 상태는 messages와 events 두 목록이다. messages는 다음 모델 호출에 보낼 대화 이력이고 events는 화면에서 확인할 실행 기록이다. 도구 실행이 끝날 때 model 이벤트와 tool 이벤트가 별도로 남는다. API가 실패해도 이전에 실행한 도구 기록을 지우지 않는다.

app/core.py: 직접 보이는 반복문

def run_react(question, chat, max_turns=3):
    if not 1 <= max_turns <= 5:
        raise ValueError('max_turns는 1~5입니다.')
    messages = [{'role': 'system', 'content': REACT_SYSTEM}, {'role': 'user', 'content': question}]
    events = []
    for turn in range(1, max_turns + 1):
        try:
            text = chat(messages)
        except (RuntimeError, ValueError) as exc:
            return {'status': 'error', 'text': str(exc), 'events': events}
        events.append({'kind': 'model', 'turn': turn, 'text': text})
        messages.append({'role': 'assistant', 'content': text})
        try:
            expression = parse_action(text)
            if expression is None:
                return {'status': 'finished', 'text': text, 'events': events}
            value = calculate(expression)
            observation = f'계산식: {expression}\n결과: {value}'
            events.append({'kind': 'tool', 'turn': turn, 'text': observation})
        except (ValueError, SyntaxError, ArithmeticError) as exc:
            observation = f'도구/형식 오류: {exc}'
            events.append({'kind': 'tool_error', 'turn': turn, 'text': observation})
        messages.append({'role': 'user', 'content': 'Observation:\n' + observation})
    return {'status': 'max_turns', 'text': '반복 상한으로 중단: 최종 답 미완료', 'events': events}

처음에는 system 규약과 원본 question 두 개만 있다. chat(messages)로 받은 응답은 assistant 메시지로 추가한다. parse_action(text)의 반환이 None이면 최종 답이므로 finished로 종료한다. 계산식 문자열이면 calculate를 실제 호출한다.

관찰값은 role="user"의 Observation: 메시지로 넣는다. 오늘은 일반 텍스트 프로토콜이므로 native ToolMessage/tool_call_id를 사용하지 않는다. 이 차이를 무시하고 native 도구 API가 실행됐다고 설명하면 안 된다. 다음 호출은 이전 assistant의 Action과 프로그램의 Observation을 함께 본다.

시점 messages의 내용 변화 events의 변화
시작 system 규약, user 문제 비어 있음
첫 응답 assistant Action 추가 model 1회
실제 계산 후 user Observation 추가 tool 1회
두 번째 응답 assistant 최종 답 추가 model 2회
종료 더 호출하지 않음 status=finished

max_turns=3은 모델 응답 횟수 상한이다. 마지막 허용 회차에서 도구를 실행했더라도 최종 답을 받지 못하면 max_turns다. 18이라는 도구 값이 있다고 이를 모델의 완성 답으로 꾸미지 않는다. 모델이 도구 없이 바로 최종 답을 내면 허용하되 tool 이벤트가 없다는 사실이 기록된다. ReAct 프롬프트가 항상 실제 도구 사용을 보장하는 것은 아니다.

모의 모델은 어떻게 움직이는가

class ScriptedChat:
    def __init__(self, record_id):
        self.expression, self.summary = FIXTURES[record_id]
        self.model, self.provider = 'teacher-script-v1', 'mock'
        self.calls, self.metrics = 0, []

    def __call__(self, messages):
        self.calls += 1
        system = messages[0]['content']
        value = calculate(self.expression)
        if 'Action: calculator' in system and not messages[-1]['content'].startswith('Observation:'):
            return f'Plan: 필요한 수량과 가격을 계산한다.\nAction: calculator\nAction Input: {self.expression}'
        if '풀이 없이' in system:
            return f'#### {value}'
        return f'계산: {self.expression} = {value}\n검증: {self.summary}\n#### {value}'

생성자는 FIXTURES에서 문제별 교사 작성 계산식과 요약을 받는다. 예를 들어 0번은 (16-3-4)*2다. 정답 answer를 읽어 모델 입력으로 넘기는 방식이 아니다. Action 이후 Observation 메시지가 오면 최종 답 형식으로 응답하는 대본이다. 이 대본 역시 calculate를 사용하므로 모든 정답 일치는 대본·프로그램 검증이며 모델 성능이 아니다.

6차시 · 동일 문제에서 기본·풀이·ReAct 결과 비교

프롬프트 효과와 모델 차이를 분리한다

기본 응답과 짧은 풀이를 비교하려면 question·공급자·모델·표본 순서를 유지해야 한다. 공급자를 바꾸면 프롬프트뿐 아니라 모델·서비스 설정도 바뀐다. 이는 “구성 비교”이며 공급자만의 효과라고 해석할 수 없다. 오늘 필수 비교는 같은 공급자에서 direct·summary·react 세 방식이다. fewshot은 3차시에서 별도 선택 비교한다.

ReAct는 추가 호출과 계산 도구를 사용하므로 조건이 완전히 같은 단일 호출 실험은 아니다. 더 많은 자원을 써서 얻은 결과라는 차이도 함께 기록한다. 정답 여부만 보지 말고 호출 수·공개 응답·도구 실행·오류 상태를 함께 읽는다.

최종 숫자를 정규화하기

def parse_final(text):
    # 마지막 줄의 #### 숫자만 허용: 단위·백분율은 수업 범위 밖이다.
    match = re.search(r'(?:^|\n)####\s+(-?\d[\d,]*(?:\.\d+)?)\s*$', text.strip())
    if not match:
        return None
    try:
        value = Decimal(match.group(1).replace(',', ''))
        return value if value.is_finite() else None
    except InvalidOperation:
        return None

문장에서 마지막 숫자만 무조건 가져오면 설명의 수량이나 날짜를 답으로 착각할 수 있다. 그래서 마지막 줄의 #### 숫자를 계약으로 정한다. 쉼표는 제거해 70,000과 70000을 같은 Decimal 값으로 비교한다. #### 18원은 이 코드에서 형식 실패이며 틀린 숫자 0으로 바뀌지 않는다. 숫자가 없는 응답과 수학 오답을 구별하려는 설계다.

원본 answer는 풀이와 최종 숫자가 함께 있는 문자열이다. 제공 표본은 literal \n을 사용하므로 사후 대조용 원본 answer에만 이를 실제 개행으로 복원한다. question이나 일반 응답 전체에 무차별 replace를 적용하지 않는다.

main.py: 예측과 원본 정답 대조

def make_result(row, strategy, chat, output, metrics=None):
    predicted = parse_final(output['text'])
    expected = parse_final(row['answer'].replace('\\n', '\n'))
    finished = output['status'] == 'finished'
    return {'record': row, 'strategy': strategy, 'mode': 'mock' if chat.provider == 'mock' else 'live',
            'provider': chat.provider, 'model': chat.model, **output,
            'predicted': str(predicted) if predicted is not None else None,
            'expected': str(expected) if expected is not None else None,
            'correct': bool(predicted == expected) if finished and predicted is not None and expected is not None else None,
            'metrics': metrics or []}

predicted는 모델의 공개 응답, expected는 원본 answer에서 추출한다. status=finished이며 두 값이 모두 있을 때만 bool로 일치 여부를 기록한다. 파싱 실패·API 오류·반복 중단은 correct=None이다. 이는 오류를 오답 숫자로 위장하지 않으면서 비교에서 미완료를 분리한다.

결과 객체에는 row가 들어가지만 이는 호출이 끝난 뒤 저장을 위한 것이다. 앞 단계 chain.invoke와 run_react에는 question만 들어갔다. 입력에 answer가 섞이지 않는 경계를 코드에서 다시 확인한다.

def failure_demo():

처음 for문은 같은 calculate 함수에 정상·실패 식을 보낸다. 예외를 잡은 뒤 예외 클래스 이름을 보여주므로 계산기 입력 문제를 API 문제로 착각하지 않는다. 두 번째 for문은 행동 파서를 검사한다. 마지막 lambda는 언제나 같은 Action을 내보내는 합성 모델이다. 2회만 허용하면 계산을 두 번 실행한 후 max_turns로 종료한다.

호출 예산과 재시도 정책

RemoteChat은 상한을 확인한 뒤 요청 횟수를 증가시킨다. 429에서 무한 재시도하면 같은 원인을 반복하고 수업 시간을 낭비할 수 있다. 이 교안은 자동 재시도 0회로 두고 Retry-After 안내를 보고 수동으로 재실행한다. 무료 한도가 찼을 때는 호출을 줄이거나 명시적으로 모의 실행을 선택한다. 다른 공급자로 바꾸면 데이터 전송 대상·모델·요금이 바뀌므로 --provider를 직접 선택한다.

실제 외부 API는 계정·모델·엔드포인트가 있어야 검증할 수 있다. 로컬 테스트의 성공을 세 원격 서비스의 성공으로 해석하지 않는다. 다음 차시는 이러한 상태와 원본 근거를 한 화면에 저장한다.

def text_block(label, value):
    return f'<h3>{escape(label)}</h3><div class="result-text">{escape(str(value))}</div>'

        body += text_block('원본 answer (표시용 개행 복원)', row['answer'].replace('\\n', '\n'))
        cards.append('<article>' + body + '</article>')
    comparable = [x for x in results if x['strategy'] != 'local']
    matched = sum(x.get('correct') is True for x in comparable)
    parsed = sum(x.get('predicted') is not None for x in comparable)
    summary = f'비교 항목 {len(comparable)}건 · 숫자 파싱 {parsed}건 · 정답 일치 {matched}건' if comparable else '로컬 구조 실습 · 모델 성능 비교 없음'
    html = f'''<!doctype html><html lang="ko"><meta charset="utf-8"><title>U2-02 실습 결과</title>
<style>{STYLE}</style><header><h1>2026-11-18 · CoT·ReAct 실습 결과</h1>
<p>제공 데이터: D04 GSM8K · <a href="{SOURCE}">{SOURCE}</a></p>
<p>{summary}</p><p>모의 대본의 정답 일치 수는 모델 성능 지표가 아닙니다. 소표본 결과를 GSM8K 전체 점수로 일반화하지 않습니다.</p>
<p>model=공개 응답 / tool=실제 로컬 계산 / mock=교사 작성 대본. 공개 풀이를 내부 사고 기록으로 해석하지 않습니다.</p></header>{''.join(cards)}</html>'''
    stem.with_suffix('.html').write_text(html, encoding='utf-8')
    return stem.with_suffix('.html')

session은 결과 파일 이름의 차시 번호이고 results는 make_result가 만든 dict 목록이다. 날짜·시각·마이크로초를 파일명에 넣어 재실행 결과를 구분한다. 같은 stem의 JSON은 다시 읽을 수 있는 구조화 기록이고 HTML은 브라우저에서 확인할 화면이다. 함수 반환값은 HTML 파일의 Path이며 HTML 문자열 자체가 아니다.

row["row_index"]·row["id"]는 제공 데이터 위치 영역에 들어간다. events의 kind가 tool이면 실제 calculate 반환 기록, model이면 공개 모델 응답이다. 모의 대본에서는 provider=mock임이 항상 드러난다. metrics는 실제 원격 요청의 seconds·usage이며 대본에서 가짜 지연/토큰을 만들지 않는다.

argparse는 어떤 실습을 실행할지 선택한다. parse_args() 결과의 session 값이 1·2·4·7이면 로컬 코드만 실행한다. 3·5·6이면 live 여부에 따라 RemoteChat 또는 ScriptedChat을 생성한다. 8이면 이미 저장한 JSON을 다시 읽어 보고서만 만든다. 따라서 8차시 재출력 자체는 API 호출 비용이 없다.

원격 비교에서 RemoteChat 객체는 한 번 생성해 재사용하므로 max-calls가 모든 선택 문제와 전략에 걸쳐 합산된다. 모의 객체는 각 문제별 fixture를 사용한다. if __name__ == "__main__": main()은 파일을 실행했을 때만 이 분기 함수를 시작하며, 테스트에서 main 모듈을 import했다고 명령행 파싱이 자동 시작되지 않게 한다.
